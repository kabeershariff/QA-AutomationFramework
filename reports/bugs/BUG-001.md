# BUG-001: Application input accepts malformed email formats

- Severity: Major
- Priority: P1
- Status: Open; confirmed on retest 2026-10-14
- Environment: Chromium, Firefox, WebKit; desktop 1280x720; https://www.applyground.work/
- Preconditions: A job detail page with the embedded simple application form is open.
- Steps to reproduce:
  1. Open `/jd?scenarios=simple-company-form&id=0&dataset=big_company_cs_1000`.
  2. Enter `not-an-email` in the Email field.
  3. Fill all other required fields with valid values.
  4. Click `Submit application`.
- Expected result: The form rejects the malformed email and shows a field-specific email validation error.
- Actual result: The live form submits successfully and returns `"validation":{"passed":true}` with an empty missing-required array.
- Evidence: Observed manually on 2026-10-14 against the deployed instance
  (`validation summary=''`, `missing=[]`, submission accepted). This defect is **not** covered by an
  automated test, by design: the only build on which it reproduces is the deployed one, and
  `qa_task.txt.txt` prohibits submitting fake applications to the live portal. The local copy in
  `mock_site` already rejects the same input — see "Root cause" below.
- Automated coverage of the expected behaviour: the rejected/rejected-equivalent path is asserted
  against the local copy by
  `tests/application_form/test_application_form.py::test_invalid_email_variants_are_rejected`
  (10 parametrized invalid addresses) and
  `::test_invalid_email_format_shows_error`. Those cases pass, so the local build is correct; they
  do not and cannot reproduce BUG-001.
- Frequency: always
- Notes / suspected root cause: The deployed validation logic checks required presence and trims
  whitespace but does not validate email syntax. The local copy validates correctly —
  `mock_site/src/lib/validation.ts:8-17` defines `EMAIL_PATTERN =
  /^[^\s@]+@[^\s@]+\.[^\s@]+$/` with a 254-character total and 64-character local-part limit, and
  `validateRequired` rejects on `expected.name === 'email' && !isValidEmail(value)`
  (`validation.ts:47`). The built bundle `mock_site/dist/assets/index-CDIoRXY3.js` contains the same
  regex, so the local build is current. The defect is therefore a **build/versioning discrepancy
  between the deployed artefact and the current source**, not a logic error in the current code —
  the deployed bundle appears to predate the email-validation fix. This is the reverse of the usual
  case and should be confirmed with the owning team before a fix is scheduled: the likely remedy is
  to redeploy from the current source rather than to change `validation.ts`.
- Regression guard: once the deployed build is refreshed, re-run the two local cases above against
  the deployed instance manually (one synthetic submission) to confirm BUG-001 is cleared.
- Retest (2026-10-14): Still reproducible. Submitting `not-an-email` with all other required
  fields valid on the live portal returned `"validation":{"passed":true}` with an empty
  missing-required array. Status remains confirmed defect.
