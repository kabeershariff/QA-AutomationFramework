# BUG-002: Application form is served and accepts submissions for a job id that does not exist

- Severity: Major
- Priority: P1
- Status: Open; reproduced 2026-10-14
- Environment: Chromium 1280x720; local portal copy (`mock_site`) served on `http://127.0.0.1:8765`
- Dataset: `big_company_cs_1000` (1000 records, ids `0`–`999`)
- Preconditions: none
- Steps to reproduce:
  1. Open `/jd?scenarios=simple-company-form&id=9999&dataset=big_company_cs_1000`.
     Job id `9999` does not exist in the dataset.
  2. Wait for the not-found state to appear (it renders only once the dataset has loaded).
  3. Fill `Full name`, `Email`, `Current location`, attach a resume, select `Yes`
     for work authorisation.
  4. Click `Submit application`.
  5. Observe the rendered validation summary and the resulting URL.
- Expected result: The page shows the not-found state and offers **no** application
  form or submit control. Submitting against a requisition that does not exist must be
  impossible.
- Actual result: The page renders the not-found banner
  (`JSONL JD id 9999 was not found.`) **and** a complete, working application form
  underneath it, with no `h1` for any job. The submission is accepted, scored, and the
  browser navigates to a success URL:

  ```
  /jd?scenarios=simple-company-form&id=9999&dataset=big_company_cs_1000
     &score=local&scoreRun=1791996661345&sec=0&filled=83%25
  ```

  carrying `"validation": {"passed": true}` and an empty `missingRequiredFields`.
- Evidence:
  - Screenshot: `reports/bugs/evidence/BUG-002-unknown-job-id.png`
  - DOM probe, after waiting for the dataset to finish loading:

    | Probe | `id=9999` | `id=0` (valid) |
    |---|---|---|
    | `[data-section='jd'][data-state='not-found']` | 1 | 0 |
    | `article h1` | 0 | 1 |
    | `[data-section='scenario-form']` | 1 | 1 |
    | `button[data-action='submit-application']` | **1** | 1 |

    Rendered body for `id=9999` ends with a live form: `Apply for this role / Full name
    * / Email * / Phone / Current location * / Resume * / …`.
  - The same happens for any unresolvable id, not just an out-of-range integer:

    | id | not-found state | submit buttons |
    |---|---|---|
    | `9999` | 1 | **1** |
    | `-1` | 1 | **1** |
    | `abc` | 1 | **1** |

  - Automated guard: `tests/job_details/test_job_details.py::test_unknown_job_id_offers_no_application_form`
    is `xfail(strict=True)` and currently fails as expected. The companion assertion
    `::test_unknown_job_id_names_the_missing_requisition` passes — the not-found copy
    itself is correct; only the form is wrong.
- Frequency: always (deterministic — this is a render-ordering property, not a race)
- Notes / suspected root cause: `ScenarioFrame.tsx` computes
  `jsonlNotFound = Boolean(requestedJdId && jsonlJobs.length > 0 && !jsonlJob)`
  (`:246`) and renders a correct not-found section for it (`:589-594`). The application
  form section is rendered **outside** that conditional chain at `:667`:

  ```tsx
  <section data-section="scenario-form">
    <h2>Apply for this role</h2>
    {children}
  </section>
  ```

  `children` is the scenario form supplied by the route, so it renders regardless of
  whether the requested job resolved. Separately, `handleSubmit`
  (`simple-company-form/index.tsx:40-47`) validates and scores without ever consulting
  whether a job resolved, so a client-side gate on the section is the only thing
  currently stopping a submission — and it is missing.
- Suggested fix: render the `scenario-form` section only when `jsonlJob` is truthy, and
  show the not-found state in its place.
- Regression guard: the `xfail(strict=True)` becomes a hard failure the day the app is
  fixed, so the guard cannot silently rot.
- Retest: pending fix.
