# BUG-003: No maximum length on the required name and location fields

- Severity: Major
- Priority: P2
- Status: Open; reproduced 2026-10-14
- Environment: Chromium 1280x720; local portal copy (`mock_site`) on `http://127.0.0.1:8765`
- Scenario: `simple-company-form`
- Preconditions: none
- Steps to reproduce:
  1. Open `/jd?scenarios=simple-company-form&id=0&dataset=big_company_cs_1000`.
  2. Enter 5000 characters in `Full name` (e.g. `"A" * 5000`).
  3. Fill `Email`, `Current location`, attach a resume, select `Yes` for work
     authorisation.
  4. Click `Submit application`.
  5. Expand `Review local submission JSON`.
- Expected result: The field declares a documented maximum length — enforced either by
  client-side `maxlength` or by a server-side rejection with a clear validation message
  — and input beyond it is refused or explicitly truncated.
- Actual result: No maximum exists at any layer. All three text inputs carry **no**
  `maxlength` attribute, validation accepts the value, and the full 5000 characters
  round-trip into the submission payload verbatim.
- Evidence:
  - Screenshot: `reports/bugs/evidence/BUG-003-no-maxlength.png`
  - DOM probe:

    | Input | `maxlength` attribute | 5000-char value accepted | Round-tripped length |
    |---|---|---|---|
    | `Full name` | `null` (absent) | yes | 5000 |
    | `Current location` | `null` (absent) | not separately probed; same code path | — |
    | `Email` | `null` (absent) | — | — |

    `"validation": {"passed": true}` with `candidate.fullName` exactly 5000 characters.
- Frequency: always
- Notes / suspected root cause: `simple-company-form/index.tsx:52-84` passes `required`
  to the `fullName` and `location` fields but never a length constraint, and
  `mock_site/src/lib/validation.ts:35-50` only checks presence, whitespace, and email
  syntax. There is no length check anywhere in the validation path.

  Note the asymmetry: `Email` *is* bounded, but only in `isValidEmail`
  (`validation.ts:12-17`, 254-character total and 64-character local-part limits) — and
  that bound is applied in JavaScript rather than via the input's `maxlength`, so the
  browser still lets the user type past it.
- Impact: in a real ATS this value reaches downstream systems — mail templates, CRM
  and database columns, CSV exports — where truncation is silent and lossy, so a
  candidate's name is quietly corrupted rather than rejected.
- Suggested fix: add an explicit `maxLength` to the `Field` component for `fullName`
  and `location`, set `maxlength` on the rendered input, and mirror the bound in
  `validateRequired` so the value is rejected server-side with a message rather than
  silently truncated.
- Automated coverage:
  - `tests/application_form/test_application_form.py::test_field_length_boundary_probe_is_defined`
    is `xfail(strict=True)` and documents the missing upper bound.
  - The low boundary is already pinned by
    `::test_boundary_name_lengths_are_accepted` (1-character name accepted).
- Retest: pending fix.
