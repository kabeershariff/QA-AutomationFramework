# BUG-005: Invalid input is reported as "missing" and no field is marked invalid

- Severity: Major
- Priority: P2
- Status: Open; reproduced 2026-10-14
- Environment: Chromium 1280x720; local portal copy (`mock_site`) on `http://127.0.0.1:8765`
- Scenario: `simple-company-form`
- Preconditions: none
- Steps to reproduce:
  1. Open `/jd?scenarios=simple-company-form&id=0&dataset=big_company_cs_1000`.
  2. Fill `Full name` = `QA Probe`, `Current location` = `Remote`, attach a resume,
     select `Yes` for work authorisation.
  3. Enter `not-an-email` in `Email`.
  4. Click `Submit application`.
  5. Read the validation summary, then inspect the `Email` input and the page for
     field-level errors.
- Expected result: The summary says the email is **invalid** (or names the field as
  needing attention), the `Email` input is marked `aria-invalid="true"`, and a
  field-associated error message is rendered next to it.
- Actual result: The summary reads

  ```
  The form is missing required answers:
  email
  ```

  The address **is present**; it is malformed. The `Email` input keeps
  `aria-invalid="false"`, and the page contains **zero** `[data-field-error]` elements.
  A screen-reader user is told a field is absent while the field is visibly filled in
  and focused, and is given no indication of which control is at fault.
- Evidence:
  - Screenshot: `reports/bugs/evidence/BUG-005-invalid-email-as-missing.png`
  - DOM probe:

    | Probe | Result |
    |---|---|
    | `[data-field-error]` count | **0** |
    | `#field-email` `aria-invalid` | `false` |
    | `#field-fullName` `aria-invalid` | `false` |
    | `[data-section='validation-summary']` text | `The form is missing required answers:\n\nemail` |

- Frequency: always — every malformed email renders this way, because the rejection path
  is shared with the genuinely-empty case.
- Notes / suspected root cause: two separate gaps combine here.

  1. **Misclassification.** `validateRequired` (`validation.ts:35-50`) pushes an invalid
     email into the *same* `missing` array used for absent fields:

     ```ts
     } else if (expected.name === 'email' && !isValidEmail(`${value}`)) {
       missing.push(expected.name);
     }
     ```

     `ValidationSummary.tsx:14-24` then renders that array under the heading
     *"The form is missing required answers:"*, so an invalid-but-present value is
     described as absent.

  2. **No per-field error channel in use.** `Field.tsx:42-46` accepts an `error` prop and
     renders `aria-invalid` plus a `role="alert"` message, and `SubmissionValidationResult`
     has a `warnings` array — but `validation.ts:51-56` always returns
     `warnings: []`, and `simple-company-form/index.tsx:52-84` never passes `error` to any
     field. The rendering capability exists and is entirely unwired.
- Impact: candidates are misdirected about what to fix, and assistive technology cannot
  associate the error with its control. `aria-invalid="false"` on a field the app just
  rejected is an accessibility defect independent of the wording.
- Suggested fix: carry a distinct `invalidFields` (or per-field error map) through the
  validation result; render it under its own heading ("These answers are not valid:")
  and pass each entry to the matching `Field`'s `error` prop so `aria-invalid` and the
  `role="alert"` message are wired up.
- Automated coverage:
  - `tests/application_form/test_application_form.py::test_invalid_email_is_flagged_on_the_field`
    is `xfail(strict=True)`.
  - Existing coverage asserts only that the string `"email"` appears in the missing-field
    list, which the current misclassification satisfies — which is why this defect was
    previously invisible.
- Retest: pending fix.
