# BUG-007: Optional phone and portfolio fields declare a type but are never validated

- Severity: Minor
- Priority: P3
- Status: Open; reproduced 2026-10-14
- Environment: Chromium 1280x720; local portal copy (`mock_site`) on `http://127.0.0.1:8765`
- Scenario: `simple-company-form`
- Steps to reproduce:
  1. Open `/jd?scenarios=simple-company-form&id=0&dataset=big_company_cs_1000`.
  2. Fill every required field with a valid value.
  3. Set `Phone` to `abc` (or `++++`, or `12345678901234567890`).
  4. Set `Portfolio or profile URL` to `not-a-url` (or `ftp://files.example.com`,
     `http://`, or a single space).
  5. Click `Submit application` and expand `Review local submission JSON`.
- Expected result: A value that cannot be a phone number or a URL is either rejected
  with a message or flagged as invalid, matching the `kind` the field declares.
- Actual result: Every value is accepted verbatim and written into the submission
  payload. `"validation": {"passed": true}` with no warnings.
- Evidence — all seven values accepted:

  | Field | Value | Result |
  |---|---|---|
  | `Phone` | `abc` | accepted, stored verbatim |
  | `Phone` | `++++` | accepted, stored verbatim |
  | `Phone` | `12345678901234567890` | accepted, stored verbatim |
  | `Portfolio or profile URL` | `not-a-url` | accepted, stored verbatim |
  | `Portfolio or profile URL` | `ftp://files.example.com` | accepted, stored verbatim |
  | `Portfolio or profile URL` | `http://` | accepted, stored verbatim |
  | `Portfolio or profile URL` | `" "` | accepted, stored verbatim |

- Frequency: always
- Notes / suspected root cause: the markup declares intent that nothing acts on.
  `simple-company-form/index.tsx:69-74` renders `Phone` with `kind="tel"` and `:75-84`
  renders `Portfolio or profile URL` with `kind="url"`, which produce
  `<input type="tel">` and `<input type="url">` in the DOM. Neither type constrains the
  value — that is native browser behaviour, not validation — and
  `mock_site/src/lib/validation.ts:35-50` only inspects `expectedFields` entries with
  `required: true` plus the email special case. Both fields are optional, so neither is
  reached at all.

  The `warnings` array that would be the natural channel for a soft warning exists in
  the model and in `ValidationSummary.tsx:25-33`, but `validation.ts:51-56` hardcodes
  `warnings: []` (see also BUG-005).
- Impact: low on its own — these are optional fields and nothing downstream consumes
  them in this build. It matters as a pattern: the form advertises typed input it does
  not enforce, so any integration that later reads `candidate`/`answers` inherits
  unvalidated data.
- Suggested fix: validate the two optional fields against the type they already declare
  and surface non-blocking failures through the existing `warnings` channel, so the
  behaviour matches what the markup advertises without making optional fields mandatory.
- Automated coverage: seven `xfail(strict=True)` cases in
  `tests/application_form/test_application_form.py`
  (`test_optional_phone_rejects_nonsense`, `test_optional_portfolio_url_rejects_nonsense`).
- Retest: pending fix.
